# ADR-002: Database Architecture

## Status

Accepted

## Context

The platform is a Go modular monolith backed by PostgreSQL. The system must keep database concerns simple, maintainable, and portable while preserving secure and deterministic identity handling for application entities.

The project is currently at the repository foundation and PostgreSQL migration setup stage. It must support modern, secure application entity identity management without introducing unnecessary database-specific extension requirements.

## Decision

### UUID Generation Decision

- All application entity UUIDs are generated by the Go application layer.
- PostgreSQL stores UUID values using the native `UUID` type.
- PostgreSQL UUID-generation extensions such as `uuid-ossp` are not required and must not be introduced without a new architecture decision.
- UUIDs must be generated using a cryptographically secure, appropriate UUID implementation in Go.
- This decision applies to new entity tables unless a future ADR explicitly changes it.

## Rationale

This keeps identity generation in the application boundary, where it is easier to test, reason about, and audit. It also keeps the database schema simpler and avoids adding PostgreSQL extension requirements beyond what the project explicitly needs.

Using the PostgreSQL native `UUID` type still preserves compatibility with PostgreSQL’s storage and indexing capabilities while avoiding unnecessary database-side extension dependencies.

## Consequences

- Application code is responsible for creating UUID values before insertion.
- Database migrations remain focused on schema and required extension support, not on UUID generation features.
- PostgreSQL remains the authoritative database, but the application layer retains ownership of entity identity generation.
- Future database or platform changes are less coupled to extension-specific PostgreSQL behavior.
- The project remains aligned with the goal of simple, maintainable, and portable database architecture.
